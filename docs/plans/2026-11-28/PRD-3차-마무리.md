## 4. 하는 것 · 안 하는 것

## 5. 단계(Phase)와 순서

순서를 정한 까닭: ① 고칠 것이 측정값을 바꾸므로 **고침을 먼저**, 측정은 고침을 합친 뒤 한 번만. ② Windows는 한 대라 **동시 2칸, 측정은 단독** → 측정을 3단계에 몰아 한 번에. ③ 인식은 가장 길지만 **재생(맥에서 순수 함수)으로 1단계부터 따로 돌릴 수** 있고, Windows가 필요한 새 장면·Snipaste만 3단계에. ④ 화면 확인은 UI가 바뀌는 고침(메모리·꺾쇠) 뒤에 해야 다시 안 본다. ⑤ 사람 몫은 막히는 순서가 없으니 모아서 마지막에.

- **Windows 2칸 규칙**: 동시에 최대 2개, 측정 일감(W23 끝 측정·W25·W27)은 단독. 브리프 첫머리는 [windows-remote-setup.md](../../handoff/windows-remote-setup.md) §5 그대로. Windows는 커밋만, 맥이 가져와 `scripts/check-windows.sh` 뒤 푸시.
- **같은 파일을 두 일감이 고치지 않는다**: W20(캡처 강조 경로: `freeze.rs`·`screen.rs`·`ink-app/capture.rs`의 강조 시각) ↔ W21(`uia.rs`·`msaa.rs`·`events.rs`) ↔ W23(`tauri-plugin-screen-ink/overlay.rs`·웹뷰 만들기). W22는 W20·W21을 합친 뒤.
- **브리지 일감은 자기 worktree**(`git worktree add ../screen-ink-wt/<일감> -b r3/<일감> origin/feat/foundation`)에서 커밋하고 브랜치를 푸시 → 총괄이 diff를 보고 합친다. 같은 작업 트리에서 서로 덮어쓰지 않게.

## 7. 진척 기록과 보고

- 원본은 `docs/progress/progress.json` 하나. 남은 항목에 `phase`를 달았고(완료 항목은 없음), 3차에서 새로 생긴 일은 트랙 "3차 마무리(PRD-3차) — 새 일"에 넣었다. 새 일이 늘어 전체 %가 한 번 내려간다(84.2% → 79.1%) — 남은 일을 정직하게 세기 위해서다. 보고서의 "남은 작업일(환산)"은 1차 계획의 일수 단위라 §5의 실제 일정(약 4일)과 다르다.
- `npm run progress`가 보고서 맨 앞 "3차 단계" 표(단계별 항목 수·작업일·진척·남은 일)를 만든다. CI가 `--check`로 어긋남을 막는다.
- **언제 갱신**: 일감 하나를 합칠 때마다(그 항목 `status`·`note` = 커밋·수치) + 단계 관문마다(§11에 결과 한 절).
- **보고 형식(단계 끝)**: 관문 표(목표 · 결과 · 판정) → 합친 커밋 → 실행한 검사(안 돌린 것은 "미실행") → 남은 일·막힘 → 다음 단계 시작 일감.

## 8. 검증

- 일감마다: 바뀐 범위 시험 한 번(Windows는 그 PC에서 `cargo test -p <크레이트>`·clippy, 맥은 합칠 때 `scripts/check-windows.sh` + 바뀐 크레이트 시험).
- 커밋·릴리스 직전 한 번: `cargo test`(워크스페이스) · `clippy -D warnings`(맥·Windows) · `npm test` · `npm run check` · `npm run progress -- --check` · 인식 재생(`cargo run -p ink-platform-fake --bin recog-replay`).
- 측정은 단독, n과 조건(모니터·배율·판 해시)을 문서에 적는다. 통과시키려고 기준을 바꾸지 않는다 — 기준을 바꾸려면 §3에 결정으로 적는다.
