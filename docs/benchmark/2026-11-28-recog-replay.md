# Windows 실제 창 287점 인식 재생 · 2026-11-28

실제 창 287점에서 첫 강조는 **217 → 261점(75.6% → 90.9%)**, 휠 두 칸 이내는 **251 → 269점(87.5% → 93.7%)**이다. 두 관문을 통과했다. 21장면에서 이전에 맞혔던 Top-1·Top-3 점을 모두 유지했다.

## 측정 조건

Windows에서 수집한 16종·21장면의 PNG, 창 목록, 접근성 요소, 자식 창, 커서와 정답을 그대로 사용했다. 맥에서 실제 고르기 서비스로 점마다 다시 진입했다. 네 변 각각의 오차가 물리 2px 이하면 적중이다. Top-1은 첫 강조, Top-3은 첫 강조 또는 휠 위·아래 두 칸 안의 적중이다. [이전 수집 조건과 점수](2026-11-27-windows-recog.md)

## 첫 강조를 놓친 70점의 원인

| 기존 재생에서 관찰한 위치 | 점 | 근거 |
|---|---:|---|
| 정답이 융합된 사슬 안에 있음 | 42 | 첫 강조에서 한 칸 떨어진 점이 28개, 두 칸이 6개, 세 칸 안에도 닿지 않는 점이 8개였다. 자식 창보다 작은 교차 상자가 앞서거나, 영상 경계가 약한 조작 항목의 점수가 낮았다. |
| 원래 접근성 경계는 맞지만 맞춤 뒤 사라짐 | 3 | 열린 메뉴의 세 행이 팝업 외곽선 쪽으로 3px씩 늘었다. |
| 입력 후보 중 네 변이 모두 맞는 사각형이 없음 | 25 | 낮은 대비의 옆 막대, 외곽선 없는 문단, 여백과 이웃 칸이 같이 잡힌 PDF, 고배율의 행·탭, 캔버스의 짧은 경계 등이 포함된다. |

- **배율**. RB-12 Win32에서는 접근성 단추가 120×32, 같은 단추의 자식 창이 240×64였다. 커서가 잘못된 접근성 요소에 들어가거나 올바른 요소를 아예 조회하지 못했다. 물리 자식 창을 쓸 수 있는 점은 융합에서 회복했다. 공급자의 좌표 변환은 Windows에서 별도 확인할 부분이다.
- **가림**. RB-18에서 앞 창은 스냅숏의 `cloaked` 필터에서 빠졌다. 남은 창에서 놓친 여덟 점은 RB-04와 같았다. 재생에서 가림 판정에만 기인한 실패는 찾지 못했다.

## 바꾼 규칙

1. 첫 강조에서 실제 자식 창과 접근성 항목의 경계를 사용한다. 행 안에 글자나 편집 레이블이 있는 경우에도 행 자체를 고를 수 있다. 독립적으로 확인된 하위 조작 요소와 문서 안의 작은 영상 후보는 계속 선택할 수 있다. 제목 표시줄은 창 위쪽에 있을 때 창 선택에 사용한다.
2. 메뉴·목록·데이터 행은 접근성에서 받은 행 경계를 유지한다. 행 사이에 선이 없을 때 창 바깥 테두리가 행 경계로 들어오는 현상을 막았다.
3. 커서 색이 이어지는 가로·세로 범위에서 사각형을 제안하고 네 변에서 안팎을 최대 16쌍씩 비교한다. 각 변에서 75% 이상이 실제 색 단차를 보일 때 낮은 대비에서도 경계를 인정한다. 모니터의 실제 끝과 부분 전처리가 끝난 위치를 구분한다. 채움과 영상 상자의 세 변이 일치하면, 채움 안에서 잘리거나 거의 같은 범위를 조금 넘어간 투영선을 합친다. 접근성 그림 안의 채움이 면적의 60% 이상이고 네 가장자리가 모두 그림 안에 있으면 같은 방식으로 여백을 걷는다.
4. 스캔라인 채우기의 방문 흔적은 가로 64픽셀씩 한 비트 마스크로 기록한다. 연결된 한 줄을 모두 방문하는 성질을 이용해 같은 픽셀의 방문 여부를 반복 조회하는 비용을 줄였다.

## 남은 점

Top-1에서 놓친 26점 중 8점은 휠 한 칸으로 도달한다. WebView2 옆 막대 1점, 도구 설명 1점, 200% 크롬 목록 4점, 캔버스·차트 카드 2점이다. 나머지 18점은 다음과 같다.

| 장면 | Top-3 미적중 | 관찰 |
|---|---:|---|
| RB-01·02·03·12·19의 문단 | 5 | 문단 전체의 배치 상자는 보이는 선이 없고 융합 사슬에도 없다. |
| RB-04·18의 목록 첫 행과 창 빈 곳 | 4 | 정답 행 너비는 720px, 보이는 목록 너비는 400px, 접근성 행 너비는 398px다. 두 빈 곳에서는 창 위에 내부 영상 후보가 여러 겹 쌓인다. |
| RB-12 Win32 | 5 | 목록 첫 행, 트리 뿌리, 첫 탭은 물리 좌표의 하위 항목 경계가 빠졌다. 제목 표시줄과 창 빈 곳도 두 칸 안에 창에 닿지 않는다. |
| RB-12 크롬 | 2 | 카드 단추와 확인란의 두꺼운 테두리 안팎을 구분하지 못했다. |
| RB-06·14 | 2 | 디스플레이 확장 단추의 보이는 경계와 접근성 여백이 다르다. 영상 틀은 아래 조작 막대와 경계가 섞인다. |

Top-3 추가 목표 98%는 미달이다. 새로운 Windows 장면 60점 이상을 쓰는 일반화 시험은 P3의 W26 일감으로 남아 있다.

## 성능과 회귀 검사

| 맥에서 측정한 강조 계산 | 이전 | 이후 |
|---|---:|---:|
| 287점의 커서 이동 입력 처리 p95 | 1.28ms | 0.82ms |
| 1080p 합성 화면의 영상 질의 중앙값 | 0.143ms | 0.103ms |
| 4K 합성 화면의 영상 질의 중앙값 | 0.281ms | 0.106ms |

재생 p95는 점별 CSV의 입력 처리 시간에서 구했다. 영상 질의는 같은 맥에서 기존 성능 시험 바이너리와 변경 바이너리를 순서를 바꿔 가며 각각 9회 실행했다. 4K 변경 후 범위는 0.102~0.110ms였다. Windows 실기에서 화면에 첫 강조가 나타날 때까지의 시간은 미실행이다.

- G3는 영상과 창 목록만으로 크롬 31/32, WebView2 30/32, 합계 **61/64(95.3%)**였다. 기존 59/64, 관문 80%다.
- 세 패키지 `ink-domain`, `ink-vision`, `ink-platform-fake`의 시험 314개와 같은 패키지의 전 대상 Clippy가 통과했다. 고정 사례 재생, 합성 16/16, 저대비 패널의 실제 화면 끝과 전처리 영역 끝을 구분하는 시험을 포함한다.
