## 수집 범위

Windows 11 25H2 빌드 26200.9974에서 주 모니터 3840×2160(200%), 오른쪽 모니터 1920×1080(100%)의 물리 좌표와 작업 영역을 보존했다. 브라우저는 독립 프로필을 썼고 문서와 탐색기 파일은 이 시험을 위해 만들었다. 시험 창의 WGC 영상·창 목록·실제 UIA/MSAA 색인·자식 창을 `SCREEN_INK_CASE_DIR`에 기록했다. 계정 표시줄·사용자 바탕 화면이 들어가지 않도록 시험 영역 바깥을 흰색으로 채웠다. [수집 도구와 사용법](../../bench/recog/README.md)

- HTML 정답은 `recog-truth`가 색 표지에서 원점·배율을 읽고 계산했다. Win32 정답은 창을 옮긴 뒤 `WM_EXITSIZEMOVE`로 정답 파일을 갱신한 다음 병합했다. 사무 문서는 미리 정한 색과 실제 렌더링한 그림으로 정답을 표시했다.
- RB-17에서 시작 메뉴 HWND는 앱이 사용하는 `EnumWindows` 목록에 없었다. 검색 상자 중앙이 시작 메뉴 소유임을 확인하고 해당 상자와 4px 여백만 화면에서 읽었다. 재생에는 뒤에 있는 시험 창과 실제 색인만 넣었다. 작업 표시줄 미리 보기의 독립 점수는 없다.
- RB-18에서는 현재 데스크톱을 전환하지 않고 시험 창 하나만 이동했다. 저장된 Z 순서에서 첫 창의 `cloaked`는 참이고 두 번째 창의 값은 거짓이다. 시험 뒤 창을 돌려놓고 만든 데스크톱을 제거했다.
- 무손실 PNG 22개의 합계는 831,393바이트다. 같은 픽셀은 여러 사례가 한 파일을 참조하며, 모니터 원점·해상도·배율은 각 사례에 남겼다.

## RB-15·16과 MSAA 실제 창

- RB-15 실제 창은 최대화 시 작업 영역과 전체 화면 시 모니터 경계를 확인했다. RB-16 실제 창은 클릭 통과, 알파 0, 모니터 전체를 덮는 알파 1 덮개를 첫 강조에서 제외했다. 실제 창 2개와 순수 판정 6개가 통과했다.
- 200%에서 DPI를 모르는 시험 창의 16논리픽셀 칸은 32물리픽셀이었다. MSAA 직접 색인 시험에서 단추 64개를 확인했다. 같은 창의 UIA 하위 트리를 비운 뒤 실제 `UiaIndex`로 요청하자 MSAA에서 온 단추 96개를 받았다. 두 시험 모두 통과했다. 개수는 시간 예산에 따라 달라지므로 시험은 단추 출처와 크기를 확인한다.

## RB-20 응답

**네 모드 모두 진입·강조 이동·종료를 확인했다. 네 모드 모두 UI 응답 100ms 초과 0회 기준에는 미달했다.** 시험 창을 오른쪽 모니터에 올리고 진입 직전 중앙의 실제 소유 PID를 검사했다. 포터블 설정을 쓴 앱 사본에 F13을 지정해 진입·종료했다. Snipaste와 사용자 설정은 그대로였다.

| 시험 모드 | 오버레이 준비(ms) | 앱 로그의 이동 최대(ms) | UI 응답 표본 | UI 응답 최대(ms) | 100ms 초과 |
|---|---:|---:|---:|---:|---:|
| 메시지 루프 멈춤 `hung` | 102 | 11.58 | 133 | 114.9 | 1 |
| 좌표 질의 멈춤 `hang-location` | 93 | 3.06 | 133 | 113.5 | 1 |
| 끝없는 자식 `infinite-msaa` | 81 | 3.73 | 134 | 108.1 | 1 |
| 좌표 질의마다 5ms 지연 `slow-msaa` | 82 | 2.86 | 134 | 111.8 | 1 |

앱 로그가 모드마다 이동 51건을 기록했다. `hang-location`에서는 MSAA 일꾼이 100ms 마감을 한 번 넘겨 앱이 해당 일꾼의 응답 대기를 중단했고, 나머지 두 접근성 모드에서는 각각 44개·3개의 대체 요소를 받았다. `WM_NULL` 감시는 진입 전부터 종료 후까지 앱 창을 검사했다. 표의 최대값이 발생한 세부 구간은 이 측정으로 특정할 수 없다. [응답 감시 스크립트](../../bench/recog/rb20-watch.ps1)

### W21 고친 뒤

**기본 빌드는 네 모드 모두 진입 중 100 ms를 한 번 넘었다.** UI 스레드의 호출 스택에서 정지 화면 픽셀을 WebView2 공유 버퍼에 채우는 `post_draw_frame`을 확인했다. W21에서는 감시 스크립트를 고쳤다. 제품 수정은 이 함수가 있는 `overlay.rs`의 담당 일감 W23에 남는다.

각 칸은 **표본 수 / UI 응답 최대(ms) / 100 ms 초과 표본 수**다. 한 표본은 앱 소유 최상위 창들을 한 차례 훑으며 보낸 `WM_NULL` 중 가장 오래 걸린 호출이다.

| 모드 | 11월 27일 기준선 | W21 기본 빌드 | W21 플러그인 최적화 대조 |
|---|---:|---:|---:|
| `hung` | 133 / 114.9 / 1 | 148 / 110.5 / 1 | 156 / 60.7 / 0 |
| `hang-location` | 133 / 113.5 / 1 | 146 / 108.7 / 1 | 158 / 66.1 / 0 |
| `infinite-msaa` | 134 / 108.1 / 1 | 147 / 111.0 / 1 | 157 / 68.2 / 0 |
| `slow-msaa` | 134 / 111.8 / 1 | 147 / 110.5 / 1 | 156 / 68.6 / 0 |

11월 28일 `b794473`에서 기본 개발 빌드와, 같은 소스에 `--config 'profile.dev.package.tauri-plugin-screen-ink.opt-level=3'`만 준 진단용 빌드를 각각 만들었다. 두 빌드 모두 `cargo build -p screen-ink --features tauri/custom-protocol`을 사용했다. 주 모니터는 3840×2160·200%, 시험 창은 오른쪽 1920×1080·100%에 뒀다. W20이 빌드와 화면 조작을 쉬는 동안 포터블 사본만 실행했다. `--empty-uia`를 썼고 `hung`에서는 시험 창 자체가 50 ms 안에 응답하지 않는 것도 진입 전에 확인했다.

감시 간격 16 ms, 이동 간격 60 ms, F13 진입·종료는 앞 측정과 같다. W21에서는 133표본을 확보하도록 이동을 50회에서 60회로 늘렸다(`-Moves 60 -HotkeyVk 124 -ExitWithHotkey`). 두 빌드에서 모두 오버레이가 열리고 닫혔고, 앱 로그는 모드마다 이동 61건을 기록했다. 이동·종료 구간의 100 ms 초과는 모두 0회였다.

**원인 구간.** 기본 빌드에서 창 목록 수집은 9~11 ms, 화면 캡처는 49~60 ms였다. 오버레이가 준비된 뒤 UI 스레드가 BGRA를 불투명 RGBA로 바꿔 공유 버퍼에 썼다. 앱 로그의 4K 전송 호출은 278.4~287.5 ms, FHD 호출은 71.9~76.1 ms였다. `hang-location`을 따로 추적하니 F13 직후에는 화면 캡처 일꾼의 `join`이 보였고, 약 158~565 ms 사이 연속 27개 스택에서 `post_draw_frame`이 보였다. 같은 UI 스레드로 보낸 두 메시지가 약 171~390 ms 구간에서 마감을 넘겼다. 두 호출이 한 차례의 창 순회에 들어가므로 표에는 초과 표본 1개로 잡힌다. 추적 실행은 표의 집계에서 제외했다. [공유 버퍼 전송 함수](../../crates/tauri-plugin-screen-ink/src/overlay.rs)

`hang-location`의 MSAA 일꾼은 두 빌드에서 각각 100 ms 마감을 한 번 넘겼다. 대조 빌드에서는 이때도 UI 응답이 기준 안에 들었다. 11월 27일 기준선에는 이 공유 버퍼 경로가 도입되기 전의 결과가 담겨 있어, 당시 초과 원인을 이번 스택으로 소급해 특정할 수 없다. 기본 빌드의 관문을 닫으려면 W23에서 픽셀 변환을 UI 스레드 밖으로 옮기고 같은 조건으로 재측정해야 한다.

**정상 앱 회귀.** 크롬 158의 독립 시험 창에서 RB-01 ‘확인’ 단추의 첫 강조는 두 빌드 모두 물리 좌표 `(4184, 462, 120, 36)`으로 실제 단추와 네 변이 일치했다. 저장 사례 재생은 RB-01 Top-1 29/32점, 전체 Top-1 217/287점이었다.

## 재생과 회귀 검사

```powershell
cargo test -p ink-platform-fake --test replay
cargo run -p ink-platform-fake --bin recog-replay
cargo run -p ink-platform-fake --bin recog-replay -- --vision-only --filter "RB-01,RB-03" --min-top1 80
```

Windows CI는 화면을 열지 않고 사례별 Top-1 적중 수와 G3 80%를 검사한다. 누락·중복 사례, 읽을 수 없는 PNG, 정답 없는 필터도 실패로 처리한다. 기준선에 0점으로 기록된 장면도 매번 재생한다. 로컬 Windows에서 같은 재생 검사를 통과했다. GitHub 호스팅 러너 실행은 미실행이다. [사례별 기준선](../../bench/recog/cases/baseline.json) · [CI 설정](../../.github/workflows/ci.yml)
