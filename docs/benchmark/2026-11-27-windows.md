# Windows 성능 실측 · 2026-11-27

캡처 오버레이 진입은 두 화면 모두 통과했다. 첫 인식 강조는 두 화면 모두 늦었고, 판서 진입·확대 전환·[그리기로]는 FHD에서만 150ms를 통과했다. 4K 실시간 확대는 82.5fps여서 Magnification API를 유지한다. 녹화는 대상에 따라 갈렸다. 영상 창은 10분 뒤 재생 가능한 MP4를 저장했고, 모니터 전체와 지정 영역은 중지 입력에 응답하지 않았다.

## 측정 조건

- Windows 11 빌드 26200, Ryzen 5 7500F(논리 프로세서 12개), GeForce RTX 4060. 주 화면은 물리 좌표 (0, 0)에서 3840×2160·200%, 오른쪽은 (3840, 0)에서 1920×1080·100%다. 모니터별 DPI 인식 스레드에서 Win32 경계와 DPI 192·96을 읽고 앱의 캡처 로그에서도 두 해상도를 확인했다.
- 기준 소스 `b32626a`에 Windows 계측을 추가하고 `npm run app:build -- --no-bundle`로 빌드한 릴리스 사본을 실행했다. SHA-256은 `555F1D483456E6A5A6AE22A88683DA48B16D1A91D16C2E1CFD2CF92418488B74`다. 다른 작업 노드의 실행·빌드가 없는 상태에서 같은 PC에서 순서대로 측정했다.
- 포터블 설정과 별도 WebView2 프로필을 사용했다. Snipaste는 실행 상태를 유지했고, 포터블 사본에서만 영역·녹화·직전 범위·모니터·활성 창·지연에 차례로 `Ctrl+Alt+F6`부터 `Ctrl+Alt+F11`까지 지정했다. 앱이 전역 단축키 16개를 모두 등록했다.
- 중앙값은 가운데 두 값의 평균을 포함한다. p90·p95는 가까운 순위법(올림)으로 계산했다. 지연의 단위는 ms다. PRD가 백분위를 정하지 않은 150ms 진입·전환과 140ms 팝오버는 이 표의 p95로 판정한다. 표본 1회는 해당 회차의 관찰값이다. [성능 목표](../PRD.md) · [단계별 관문](../prd/07-plan.md) · [첫 강조 기준](../prd/08-smart-capture.md)

## M1 캡처 진입과 첫 강조

기본 모니터 강조를 띄운 뒤 포인터가 처음 움직여야 인식 후보 사슬을 계산한다. 주 화면과 오른쪽 화면에서 각각 100회, 단축키를 누르고 커서 쪽 웹뷰가 표시되자마자 포인터를 같은 거리만큼 움직였다. 두 모니터를 연결한 채 커서 위치만 바꿨으므로 GDI 캡처 단계에는 매번 두 화면이 모두 들어간다.

## WGC 첫 프레임·바로 캡처·트레이

바로 캡처는 실제 단축키 입력부터 Windows 클립보드의 일련번호가 바뀌고 앱이 올린 DIB 그림을 읽을 수 있을 때까지 쟀다. 오른쪽 FHD에서 직전 범위는 175×124px, 모니터와 활성 시험 영상 창은 1920×1080px였다. WGC 로그는 같은 활성 창 회차의 `StartCapture`부터 첫 프레임 수신까지다. 창 항목 생성, GPU에서 읽기, 그림 인코딩과 복사는 WGC 첫 프레임 시간 밖에 있다.

바로 캡처 세 종류에는 별도의 지연 목표가 없다. 지연 캡처는 서비스가 250ms 주기로 만료를 확인하고 일반 영역 선택을 열었다. 선택창이 포커스를 얻자마자 Enter를 보내야 클립보드 결과가 생겼다. 6.2의 '대화 없이 클립보드' 요건과 구현이 다른 지점이다.

트레이 20회는 앱 소유 트레이 창에 Windows 셸과 같은 단추 놓기 알림을 보낸 시점부터 측정했다. 매번 창이 실제로 보이고 다시 닫힌 것을 확인했다. 앱 로그의 끝점은 미리 만든 창의 표시 호출이 성공해 돌아온 순간이다. 외부 관찰은 Win32 가시성 및 다음 DWM 동기화까지이며 물리 마우스·패널 광출력 지연은 포함하지 않는다.

## M6 실시간 확대

로컬에서 만든 1920×1080·30fps H.264 시험 영상을 커서 모니터 전체에 반복 재생했다. 화면마다 `bench/m6-zoom.ps1 -Seconds 60 -AutoZoom`을 두 번 실행하고, 종료 로그의 확대 루프 횟수와 시간을 사용했다. 2배 확대에서 한 바퀴는 `MagSetWindowSource` 호출 한 번이다. PresentMon은 설치된 실행 파일을 찾지 못해 앱 Present와 DWM Present 측정은 미실행이다.

| 화면·회차별 지표 | n | 중앙값 | p90 | p95 | 최대 | 판정 |
|---|---:|---:|---:|---:|---:|---|

| FHD 루프 평균(fps) | 2 | 82.5 | 82.5 | 82.5 | 82.5 | 30 통과 |
| 4K 회차별 최장 간격(ms) | 2 | 18.5 | 19 | 19 | 19 | 참고 |

각 회차는 60.9초였다. 루프 횟수는 4K에서 5,021·5,021, FHD에서 5,020·5,021이었다. 두 해상도 모두 30fps를 넘었으므로 이 PC의 5.4 결정은 **Magnification API 유지**다. 82.5는 앱의 원본 위치 갱신 회수이며, 영상 자체는 초당 30장의 시험 패턴이다. [M6 측정 방식과 2안 판단 기준](../../bench/m6-zoom.md)

## 1080p30 녹화

마이크를 끄고 1080p30 시험 영상을 반복 재생했다. 앱의 시작 로그에서 대상 종류와 1920×1080·30fps를 확인했다. 창 녹화는 시작 확인 600초 뒤 중지 단축키를 눌렀다. CPU는 앱과 WebView2 자식의 프로세서 시간을 전체 논리 프로세서 12개로 나눈 값이다. 시작·마무리 경계를 제외한 약 595초를 2초 간격과 프로세스 열거 시간으로 표본화했다.

| 오른쪽 FHD 모니터 전체 | 1 | 실패 | 시작 로그 뒤 UI가 응답하지 않았다. 10분 뒤 중지 키를 보냈으나 저장 로그와 결과 파일이 없었다. 시험 사본을 종료한 뒤 임시 MP4에 `moov`가 없어 디코딩할 수 없었다. 프레임 누락과 완성 파일 크기는 측정 불가다. |

창 녹화의 출력 타임스탬프에는 빈 간격이 없었다. 같은 길이의 30fps 출력보다 앱이 제출한 샘플이 **1,958장(10.88%) 적었다**. 녹화기는 WGC에서 밀린 프레임 중 최신 장면만 가져오고, Media Foundation은 일정한 간격으로 출력했다. 따라서 출력 헤더만 보면 입력 누락을 놓친다. 모니터·영역의 중지 실패까지 포함해 6.3의 '10분 끊김 없이 저장'은 **미달**이다.

실제 내용도 비교했다. 6초 원본의 180장 중 녹화창에 보인 왼쪽 위 범위를 같은 밝기로 변환한 뒤, 64×36과 128×72에서 움직임이 큰 점 200개·450개의 평균 절대차로 원본 프레임 번호를 각각 찾았다. 두 해상도 모두 최선의 오차가 6/255 이하이고 차순위와의 격차가 0.5/255 이상인 프레임만 채택했다. 양쪽에서 식별한 7,907장은 번호가 모두 일치했다. 연속으로 식별된 **7,362쌍에서 원본 815장이 건너뛰어졌고 같은 장면이 928번 반복됐다**. 원본 번호 증가량은 중앙값 1, p90·p95·최대 2였다(원본 반복 경계는 순환 계산). 나머지 구간은 집계에서 뺐다. 815장은 확인한 최소 누락 수이고, 1,958장은 전체 파일의 출력 프레임과 인코더 제출 수의 차이다.

두 저장 실패는 `recording started` 직후부터 녹화 범위 표시 창이 숨김 상태로 남았다는 공통점이 있다. `rec_frame::sync`는 모니터·영역에서는 서비스가 상태를 알리는 도중 창 이동·크기 변경을 요청하고 창 녹화에서는 이 경로를 건너뛴다. 다음 조사 지점은 이 호출과 WebView2 창 메시지의 잠금 재진입이다. 대기 체인 조회로 교착을 확정하지 못했다.
