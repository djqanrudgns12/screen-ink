## 측정 조건

- 기준 소스는 `origin/feat/foundation`의 `ab7684c`다. Windows 11 빌드 26200, Ryzen 5 7500F(논리 코어 12개), GeForce RTX 4060에서 측정했다. 모니터별 DPI 인식 스레드에서 주 화면 3840×2160·200%(원점 0,0), 오른쪽 1920×1080·100%(원점 3840,0)를 확인했다.

## 숨긴 웹뷰와 첫 진입

1안은 웹뷰 문서가 준비될 때 최상위 창의 실제 표시 상태를 읽는다. 숨긴 창은 `ICoreWebView2_19::SetMemoryUsageTargetLevel(Low)`로 시작하고, Win32 창이 나타나면 `Normal`, 숨으면 다시 `Low`로 바꾼다. 이 방식은 네이티브 표시 함수를 쓰는 캡처 오버레이와 확대 창에도 적용된다. 모니터별 오버레이는 시작 때 미리 만든다. [WebView2 메모리 목표](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_19)

M1은 `bench/m1-overlay.ps1` 사본에서 포터블 설정에 맞춰 전송 키만 F13으로 바꿨다. 커서를 각 모니터의 시험 배경 위에 두고 100회씩 진입·종료했다. 누른 뒤 대기와 다음 회차까지 간격은 각각 350 ms다. 앱의 `overlay ready`는 단축키에서 네이티브 정지 화면을 그린 시점까지다.

첫 진입은 앱을 매번 다시 시작하고 4K→FHD→4K→FHD 순서로 시험했다. W5의 물리 좌표 한 줄 표본기로 양쪽 오버레이가 모두 보이는 시점부터 화면마다 단색 기준점 4개를 동시에 읽었다. 한 화면의 4개 점이 모두 검으면 해당 표본을 검은 화면으로 집계했다. [W5 혼합 배율 시험](../qa/2026-11-27/win-mixeddpi.md)

| 모니터와 지표 | 각 판의 표본 수 | 기준 | 수정 |
|---|---:|---:|---:|
| 4K M1 중앙값 / p95 / 최대(ms) | 100 | 61 / **66** / 71 | 62 / **66** / 75 |
| FHD M1 중앙값 / p95 / 최대(ms) | 100 | 62 / **66** / 69 | 61 / **66** / 68 |
| 혼합 배율 첫 진입 중 검은 화면(회) | 4회 × 32표본 | 0 | **0** |

첫 예비 실행에서 시험 배경의 오른쪽이 가려져 기준판 실기를 다시 돌렸다. 위 표는 두 판 모두 같은 맨 위 시험 배경에서 대상 창의 소유 프로세스를 확인한 실행으로 집계했다.

**채택한 안은 1안이다.** 두 모니터의 M1 p95가 모두 66 ms였고 첫 진입 128표본에서 검은 화면이 0회였다. 대기 메모리와 진입 관문을 함께 통과해 2안(`TrySuspend/Resume`)과 3안(드물게 쓰는 화면을 늦게 만들기)은 미실행이다.

## 공유 버퍼 전송

UI 스레드가 WebView2 공유 버퍼를 만들고 파일 매핑 핸들을 복제한다. 일꾼이 이 핸들로 쓰기용 뷰를 열어 BGRA를 불투명 RGBA로 변환하며 버퍼를 채운다. 쓰기가 끝나면 매핑을 닫고 UI 스레드가 세션과 모니터를 확인해 웹뷰에 읽기 전용으로 게시한다. 종료된 세션은 버퍼를 반납한다. WebView2 COM 객체는 생성한 스레드에서 사용하고 해제한다. [WebView2 공유 버퍼](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2sharedbuffer) · [WebView2 스레드 규칙](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/threading-model) · [W21 원인 측정](2026-11-27-windows-recog.md#w21-고친-뒤)

### RB-20 응답

W21과 같은 기본 개발 빌드(`cargo build -p screen-ink --features tauri/custom-protocol`)로 검사했다. 오른쪽 FHD에 `rb20-frozen --empty-uia --slow-ms 5` 시험 창을 띄웠다. 각 모드에서 `bench/recog/rb20-watch.ps1 -Moves 60 -HotkeyVk 124 -ExitWithHotkey`로 진입 전부터 종료 뒤까지 16 ms 간격으로 최상위 창의 응답을 감시했다.

| 모드 | W21 기본 최대(ms) / 초과 횟수 | 수정 표본 | 수정 p95(ms) | 수정 최대(ms) | 100 ms 초과 | 4K 일꾼 변환·쓰기(ms) |
|---|---:|---:|---:|---:|---:|---:|
| `hung` | 110.5 / 1 | 158 | 0.9 | 69.7 | 0 | 280.5 |
| `hang-location` | 108.7 / 1 | 158 | 1.0 | 65.1 | 0 | 294.3 |
| `infinite-msaa` | 111.0 / 1 | 157 | 0.4 | 86.4 | 0 | 306.9 |
| `slow-msaa` | 110.5 / 1 | 158 | 0.5 | 73.8 | 0 | 287.3 |

네 모드 모두 캡처 창이 열리고 닫혔고, 총 631표본에서 100 ms 초과·메시지 시간 초과·호출 실패가 모두 0회였다. 최대 86.4 ms로 늘려 잡은 80 ms는 넘었다. `hang-location`에서는 MSAA 일꾼의 100 ms 마감 로그가 1회 찍혔고 UI 응답 최대는 65.1 ms였다. 앱은 모드별 이동 61~62건과 두 모니터의 버퍼 게시 완료를 기록했다.

별도 릴리스 세션에서 서로 다른 단색 시험 배경을 띄우고 실제 웹뷰가 받은 버퍼를 확인했다. 4K 33,177,600바이트와 FHD 8,294,400바이트 모두 첫 픽셀의 RGBA 네 채널이 기대값과 일치했고, `releaseBuffer` 직후 두 버퍼의 길이가 0이 됐다. 이 검사용 실행은 성능 표본에서 제외했다.
