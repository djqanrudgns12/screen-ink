# Windows 4K 첫 후보 강조 실측 · 2026-11-28

4K에서 오버레이 준비 후 첫 후보 강조까지 p95가 **33.1 → 29.6 ms**, FHD에서는 **26.6 → 22.9 ms**였다. 각 화면에서 수정 전후 100회씩 측정했다. 두 화면 모두 30 ms 목표를 통과했고, 오버레이 준비와 인식 Top-1도 기준을 충족했다. [3차 계획 §5.1](../plans/2026-11-28/PRD-3차-마무리.md#51-p1--고침--맥-실기)

## 측정 조건

- Windows 11 Pro 빌드 26200, Ryzen 5 7500F(논리 프로세서 12개), GeForce RTX 4060. 모니터별 DPI를 인식하는 Win32 스레드에서 주 화면 (0, 0) 3840×2160·200%와 오른쪽 (3840, 0) 1920×1080·100%를 확인했다. 매회 두 모니터를 모두 캡처했다.
- 기준은 `origin/feat/foundation`의 `b794473cf41b112e69882f6b573ee90b6572deba`에 첫 강조 구간 로그만 추가한 판이다. 개선판은 이 문서와 함께 커밋한 소스다. 두 판 모두 `npm run app:build -- --no-bundle`로 빌드한 릴리스를 `C:\agents\runs\W20-highlight4k\app\`에 복사했다. 실행 파일 SHA-256은 기준 `08447E70B73DC95EE7BA26BBC96C7B2A716804AF16B86FEEB540029FDC7FF1E0`, 개선 `D77CDB81C7D22516B28893AD4ED9B2329E46B20171A2CD2FE3CB26A8DF3BD1C8`이다.
- W21 종료 후 `C:\agents\status.ps1`에서 W20 단독 실행을 확인했다. 각 측정 시작 전에 다른 빌드·앱 사본이 없는지도 확인했다. 두 판에 같은 포터블 설정, 전용 WebView2 프로필, 디버그 로그와 W7의 격자 시험 창을 사용했다.
- 각 모니터 왼쪽 위 기준 (481, 420)에 커서를 놓고 60 ms 뒤 `Ctrl+Alt+F6`으로 진입했다. 커서 쪽 정지 창과 투명 입력 창이 보이면 (500, 420)으로 옮기고, 이후 2 px씩 총 9개 위치에 12 ms 간격으로 포인터를 보냈다. 180 ms 뒤 같은 키로 닫고 270 ms 쉬었다. 제자리 진입 확인은 표본에서 제외했다. [기존 M1 측정 방법](2026-11-27-windows.md#m1-캡처-진입과-첫-강조) · [M1 로그 집계 기준](../../bench/m1-overlay.ps1)
- `overlay ready`는 단축키 수신부터 네이티브 정지 화면을 그릴 때까지, `highlight first`는 같은 시작점부터 후보 사각형을 네이티브 창에 반영할 때까지다. 회차마다 두 로그가 한 쌍인지 확인하고 차이를 구했다. p95는 100개를 정렬한 95번째 값이다. 기존 W16의 37.8·25.2 ms는 화면당 12회였다.

## 첫 강조 구간

| 구간별 p95 (ms) | 4K 전 | 4K 후 | FHD 전 | FHD 후 |
|---|---:|---:|---:|---:|
| 준비 → 첫 이동 처리 시작 | 27.07 | 25.40 | 22.94 | 19.69 |
| 첫 이동 처리 시작 → 후보 계산 완료 | 2.82 | 2.25 | 2.19 | 1.78 |
| 후보 계산 완료 → 네이티브 그리기 호출 | 0.10 | 0.10 | 0.08 | 0.10 |
| 네이티브 그리기 호출 → 첫 강조 반영 | 2.70 | 2.85 | 1.84 | 1.67 |

가장 오래 걸린 첫 구간에는 투명 입력 창 표시, 시험 포인터 이동, 앱이 그 이동을 처리하기까지의 시간이 들어간다. '첫 이동'은 실제 후보 사슬을 만든 이동을 선택기가 처리하기 시작한 시각이다. 각 구간의 p95는 독립적으로 구했다.

창 표시와 겹쳐 실행되는 영상 전처리가 4K와 FHD 원본을 공유하도록 해 진입당 전체 화면 복사 약 39.6 MiB를 없앴다. 바로 위와 픽셀이 모두 같은 줄은 두 줄 사이에 가로 경계가 없고 세로 경계의 열도 같다. 이때 앞줄의 경계 열만 연장해 누적합과 선분을 만든다. 후보 계산에서는 같은 색이 이어진 구간의 방문 표시를 64픽셀 단위로 묶었다.

네이티브 그리기에서는 강조가 걸친 원본 행만 GDI에 넘긴다. 여러 변경을 함께 측정한 결과, 4K에서 줄어든 구간은 이동 처리 전과 후보 계산이었다. 4K 그리기 자체의 p95는 0.15 ms 늘었다.

## 인식과 화면 확인

- 실제 창 21개 장면 287점 재생에서 Top-1 **217점**(75.6%), Top-3 **251점**(87.5%)이었다. 저장된 기준 CSV와 점별 첫 후보 IoU, 정답까지의 단계 수, 경계 오차가 287점 모두 일치했다. [점별 기준선](../../bench/results/recog-replay.csv)
- 두 모니터에서 제자리 진입 시 첫 후보 로그가 생기지 않았다. 별도 픽셀 검사에서 네이티브 정지 창의 강조 안쪽 4점은 원본 RGB와 일치했고, 바깥 1점은 각 채널의 절반과 일치했다. 투명 웹뷰까지 합성한 바탕 화면에서는 일부 안쪽 점의 RGB가 원본과 달랐다. 위 픽셀 일치는 정지 창 자체에서 읽은 결과다.
- 지정한 세 크레이트의 `cargo test`는 96개 통과, 기본 제외 11개였다. 동일한 색의 줄을 개별 검사한 경우와 경계를 재사용한 경우의 누적합·선분·후보를 대조하는 시험도 통과했다. 같은 세 크레이트의 `cargo clippy --all-targets -- -D warnings`와 릴리스 빌드가 통과했다. 맥 실기는 미실행이다.
